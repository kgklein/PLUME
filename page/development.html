Developer APIs, verification and historical reports

Manual home · Numerics · Input contract

The scientific user entry points are the manual and input workflows, not a list of generic internal procedures. FORD-generated API documentation remains useful for developers tracing exact signatures and source comments. It is not an alternative authoritative definition when historical comments conflict with current equations, output writers or tests.

Dependency map

plume program -> functions: parse indexed namelists and validate
              -> map_search / refine_guess / scan loops
                 -> disp: composition/normalization dispatch
                    -> kinetic or auxiliary kinetic response
                    -> cold susceptibility
                    -> species susc + total lam + determinant
                 -> electromagnetic fields and species moments
                 -> corrected local heating/energy snapshots -> companion writer
                 -> mode/tensor writers

Species chi uses ordinary dimensionless susceptibility; lambda includes vacuum and electromagnetic terms once. solver_* are derived thermal coordinates, not authoritative physical inputs. Cold-reference and fully cold dispatch must not construct a physical zero-temperature gyroradius. Heating derivatives must not leave global state at the real or perturbed frequency rather than the accepted complex mode.

fpc Historical all-kinetic FPC distribution/debug routines

The new numerical modules follow compiler-promoted production real/complex kinds and strict IEEE behavior where required. Do not assume nrtype::DP is binary64 under every promoted build. The Faddeeva C ABI explicitly uses the ISO C double-complex interface. Shared kinetic includes avoid independently edited copies of the equations; fixed128 compiler-sensitive arithmetic is protected by exact tests.

Verification

make -j2
MPLCONFIGDIR=/tmp/plume-mpl python3 -m unittest discover -s tests -p 'test_*.py' -v

Tests include independent cold fluid/current solutions, NHDS/Stix tensor references, SciPy/Faddeeva and optional arbitrary precision, componentwise susceptibility checks, roots, field/nullspace/Faraday checks, energy derivatives, reader markers, wrapper roundtrips and checked Fortran builds. A passing suite is evidence for those cases, not universal validation of collisional/FPC or strong-mode interpretations. Exact expected data should not be edited to hide numerical changes. Historical reproduction identifies the pinned comparisons and settings.

Local documentation build

The current manual sources are the Markdown files in docs/, with docs/index.md as the homepage and images in docs/assets/. The GitHub overview remains in the root README.md. From the repository root, run:

./scripts/build_docs.sh
xdg-open docs_out/page/index.html

The script requires Python 3, FORD and Graphviz. It stages the complete manual in a temporary directory, converts local Markdown links without changing the sources, and generates API documentation from the current Fortran sources. Historical reports remain in tests/ and are linked through the evidence index below rather than listed in primary navigation.

Before replacing docs_out/, the builder checks all manual pages, local links, fragments, images, parameter anchors, rendered tables, math markup and linked API destinations. It preserves the previous output in a uniquely named backup. Detailed validation results and separate generated API link issues are recorded in docs_out/validation.json; FORD warnings are recorded in docs_out/build.log. The checker can also be run independently:

python3 tests/check_user_manual.py --site docs_out

The documentation CI workflow uses the same builder and retains its existing publication triggers. Running the local script does not deploy a website or fetch the optional ADS citing-paper list. External references are not certified by local link checks, and MathJax uses an external CDN. Existing FORD interface anchor defects and source-comment parsing warnings can remain even when manual validation passes; inspect the generated reports rather than treating a successful build as scientific validation.
